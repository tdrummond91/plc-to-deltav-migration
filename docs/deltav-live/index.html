06 / Export files · references · code ownership

What connects to what — and where your code goes

A Live export is a snapshot of a saved configuration item. Read it as an object plus its dependencies: what it owns, what it references, and what triggers its behavior. The four suffixes below describe the four kinds in your reported export; Live can export other kinds too. [1]

Evidence boundary: the filenames and suffix mappings below come from your export listing. Their item behavior is grounded in the supplied help. The actual XML files have not been inspected, so the illustrated connections are examples, not a verified dependency graph of DI_fp. The supplied help’s filename table does not enumerate these four suffixes.

1 · The four item types and what each owns

.cd.ahc · Contextual display

DI_fp.cd.ahc

A document used for contextual UI, such as a faceplate, detail display or custom popup. “Contextual display” is the item type; “faceplate” is a role it can serve.

It owns its placed content and document settings, variables, events and timers. A placed linked GEM refers to a separate GEM class; it does not make the class a child definition of this document.

Inspect ContextualDisplay → [9] [4]

.gc.ahc · GEM class

Library_CD_ACK_ALL.gc.ahc

The reusable definition: graphic elements, custom properties, variables and behavior used by its instances. Instances supply configuration such as a tag or options.

Linked instances retain the relationship to the class. Unlinking changes that relationship; nested linked GEMs can still retain their own class links. CD in this name is a naming convention, not the export type.

Inspect GEMClass → [3] [4]

.cf.ahc · Library function

Library_F_AlarmColor.cf.ahc

A shared, typed value conversion: inputs → optional calculations → rule-, value- or script-based conversion → result. A ColorFunction returns a color; a FontFunction returns a font.

The seven result families are Color, Font, Boolean, Image, String, Measurement and Number. This is suitable for reusable evaluation logic. It is not a general-purpose VBA project containing arbitrary forms and event procedures.

Inspect functions and their types → [5] [13]

.sv.ahc · Library standard

Library_S_ButtonColor.sv.ahc

A shared typed value referenced by consumers. Types include Color, Font, Boolean, Image, String, Private String, Multi-language String, Measurement and Number.

A color standard can provide theme-specific values; multi-language strings carry translations. A standard is not a writable runtime global or a container for event scripts.

Inspect standards and their types → [6] [14]

The filename is not the API. Do not infer a callable function signature, namespace, instance tag or XML ID from Library_F_AlarmColor.cf.ahc alone. Use Graphics Studio’s browsers and Script Assistant to inspect the actual name, type and arguments. [11] [5]

2 · Follow a faceplate’s references and execution

Illustrative relationship model: your exports may have different edges. A definition can be referenced by many consumers, and one consumer can reference many definitions. Having four file kinds does not imply one fixed four-file chain.

  1. Owns placed content
    Contextual display: DI_fp
    • Contains graphic elements and placed GEM instances.
    • Holds its own context, variables, document events and timers.
    • May reference standards and functions directly as well as indirectly through GEMs.
  2. Instance references definition
    Placed linked GEM → Library_CD_ACK_ALL
    • The instance provides its configured options/context.
    • The GEM class defines shared appearance and behavior, including its contained controls and interactions.
    • A click interaction may execute an action. The filename alone does not prove which action or which parameters it affects.
  3. Properties reference shared values and conversions
    Examples of independent dependency branches
    • A button’s fill property → Library_S_ButtonColor → a color value.
    • An alarm element’s color expression → Library_F_AlarmColor → a color calculated from supplied inputs.
    • A function’s configured defaults or conversion logic may themselves reference standards. Check the actual definition; this is not required for every function.

Two different flows: ownership determines where a script or variable is saved. Runtime evaluation determines when a property needs a value. A click handler runs on its event; a property expression is evaluated to supply a value. Put commands such as writes or window opening in an explicit interaction/event, rather than treating a color calculation as a click handler. [5] [7] [9]

References survive as configuration relationships

.ahc files are XML exchange documents. Import reconstructs configuration; the runtime uses published configuration. It does not resolve a GEM by loading a neighboring .gc.ahc file like a JavaScript module. Export, import, publish and refreshing loaded runtime content are separate steps. [1] [12]

The help explicitly describes standards/functions resolving by the expected type and name in the library. A missing dependency can leave a broken reference even if import succeeds; use Verify. The precise XML fields used to serialize identities and links must be established from the actual files, not guessed. [6] [5]

Update behavior differs: standards and functions are published as library items. GEM classes are not published directly; their graphical changes reach runtime through publishing the displays that use them. A successful export is not a deployment. [6] [5] [3] [12]

3 · The four export settings are separate from the four item types

In Graphics Studio → select the item → File → Export, these settings control the package. They do not select a programming language or change the item’s type. [2]

Export settingWhat it does / when it helps
Include additional identifying informationCreates ExportMetadata.log with provenance including System ID, user and graphics database name. Useful for distinguishing exports from different systems.
Include dependent itemsIncludes items on which the selected item depends. The help’s example is a display whose linked GEM requires its GEM class. Use this for a faceplate’s dependency package; do not assume it captures arbitrary external files or names dynamically built in scripts.
Include unmodified out-of-the-box itemsIncludes unchanged DeltaV-installed items, which are otherwise omitted. A dependency package can therefore differ with this setting even when the faceplate itself is unchanged.
Compress into zipped folderPackages the .ahc files together in a ZIP. It changes packaging, not the reference model.

Save first: export uses the last saved version. Exporting to the same folder can overwrite existing same-named exports, so use separate folders for comparison snapshots. [1]

4 · Where User.fxg, timed code and embedded picture code go

There is no single “Live User.fxg.” Operate’s User/SIGlobals files can hold VBA code, global variables and threshold/color tables. Split those responsibilities by value, state, event and lifetime. Example: a diagnostic popup refreshing every second

Place the popup’s OnOpen initialization, local variables and 1000 ms timer on the contextual display. Put reusable device appearance/interaction in its GEM class. Put “status → color” conversion in a ColorFunction and the common font/translated labels in standards. All these pieces can be in the export package, but the timer remains owned by the contextual display. If the task must continue after the popup closes, change the execution design rather than relocating the script to a standard.

TypeScript is the script language, not a deployment boundary. A .cd.ahc or .gc.ahc can contain script-bearing configuration. Do not expect every script to appear as a standalone .ts file or every script-bearing export to have .cf in its name. Exact XML script fields and escaping must be read from the export. Script Assistant’s All Scripts view helps inventory the active display or GEM class. [11]

5 · How to read the XML without guessing connections
  1. Start with the selected root. For this faceplate, begin with DI_fp.cd.ahc. Identify its declared item identity and type, then its contained objects.
  2. Separate ownership from references. Record an object’s local configuration and parent separately from links to a GEM class, library standard, function or target document.
  3. Follow instance → class. Match the export’s actual class reference to the GEM definition. Record instance-specific options and inspect the class’s own dependencies, including nested GEMs.
  4. Trace values back to their sources. A property can be a literal, standard, variable, parameter reference or expression/function result. Follow each reference until you reach its definition or an external runtime input.
  5. Inventory behavior by owner and trigger. Record owner, event/action/timer, inputs, outputs/writes and external dependencies. Search for a known script marker from Script Assistant; XML may escape or encode text.
  6. Use the export report and Verify together. Compare packages with dependencies enabled/disabled. An exported library item may be an indirect dependency; its presence alone does not prove a direct link from the root. A missing file may be an excluded unmodified installed item.
  7. Validate round trips in the intended version. Import and verify on an engineering/test system, then test behavior in Live. XML well-formedness alone does not prove correct references, event timing or runtime results.

To turn the illustrative chain into your actual graph, inspect one .cd.ahc and its exported dependent files together. The questions are: which exact XML fields encode identity, ownership, links, instance values and scripts? No field names or ID formats are assumed in this guide.
