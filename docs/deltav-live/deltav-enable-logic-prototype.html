Model, semantics and what this prototype proves

The JavaScript renderer creates SVG nodes from a data model once, then updates existing node values and edge classes. It is an ordinary browser prototype. Its use of browser DOM/SVG APIs is not evidence that a DeltaV Live graphic script can call those APIs or create native graphic elements.

It demonstrates a reusable rendering design and operator interaction. It does not demonstrate a Live import, native GEM instantiation, controller reads, an exact reproduction of your logic, or a performance improvement in Live.

All node values are simulated. Batch code 1 is an invented nonzero example; it is not a verified numeric code for the screenshot’s ProcWait name. MW is left as an abbreviation because its full meaning has not been supplied. Hover descriptions are explanatory draft text; the screenshot’s “R540 Batch Temperature Control SBC” is used as reference wording, not as a verified database description.

The demo uses a non-retentive two-second on-delay. False resets elapsed time; unavailable batch data resets the timer and makes the overall output UNKNOWN. Pausing freezes simulated time. A real display should show the actual controller timer/output and its quality rather than assuming these timer semantics or evaluating controller code as JavaScript.






02 · What would be generated for Live?
Expression / FHX→Parsed model→Layout + bindings→Validated .ahc→Import / Verify / Publish


Engineering-time generation
Proposed path: a Python tool reads a validated source expression, builds a syntax tree, lays out the graph and creates only the needed instances using an observed Live export format.
Keep the shared parameter, NOT, AND, comparison and timer presentations in GEM classes. Store actual instance placement, options and bindings in the contextual display. Share colors, fonts and conversion rules through standards/functions.
The diagram’s structure stays stable until the source expression changes. Regenerate and verify after that change. More generated displays may be needed, so generation must include provenance and dependency tracking.
Runtime operator view
Opening the contextual display loads its prepared graph. Native bindings supply actual values and status; configured interactions provide descriptions, drill-down and navigation.
Do not reparse or rearrange a fixed expression every refresh. Refresh values separately from structure. Measure call-up time, usable-data time and the Live complexity indicators before claiming a performance gain. [Info page]
Per-instance quality, read failures and stale configuration must be visible. Intermediate viewer calculations are diagnostic; controller results remain authoritative.

Shared code does not run simply because it exists. A function needs a consumer; an event needs a trigger; a timer needs an open owner. Configure-preview/Quick Online View results also do not prove background execution or full station behavior.


For this view: OnOpen selects the diagnostic context; bindings supply values; hover actions show descriptions; GEMs/functions share presentation and calculations. Use a timer only for a genuine periodic UI task, not to redraw a static graph.





04 · What “TypeScript access” actually means
The supplied help documents a hosted TypeScript scripting environment with selected standard objects and Emerson APIs. It does not identify the exact compiler version or prove compatibility with Node.js, npm modules, React, arbitrary DOM manipulation or every browser API. Check each target version/build rather than assuming v14, v15 and v16 expose the same surface.


Documented objects
  • Boolean, Date, Math, Number, String and selected global functions such as parseInt/parseFloat. [Built-ins]
  • DL: open displays/contextual displays, popup operations, tooltips, geometry queries and session store. [DL]
  • DLSYS: Live parameter-path reads/writes and status-bearing results. The documentation distinguishes DVSYS for converted Operate path syntax. [Data APIs]
  • Other documented host objects: DLPATH, ENV, SQL, Placement, Region, RtValue and table functions. Availability of a name does not grant every operation a general application environment would support. [Host APIs]
Three different meanings of “object”
  1. Data object: a record containing a tag, node type and inputs. It can describe a diagram without displaying anything.
  2. Native graphic object: a GEM, text element, connector or control owned by Live configuration. A runtime creation API is not established in the supplied reference.
  3. Web object: an SVG/DOM element inside an independently hosted page. This prototype creates these; they are not native Live elements.
A function named OpenDisplay opens configured content. Placement/Region describe positioning; their existence does not establish a shape factory.


Small script probes to export — not a production code library
In a disposable test display, select a Text element and name it ProbeText. Select a Button → Interaction → Click Action → Custom Script. Use Script Assistant to confirm the generated object references before inserting this host-context-dependent example:
const marker: string = "DV_PROBE_CLICK_001";
Dsp.ProbeText.Label = marker;
This checks a typed local declaration and an existing element’s property assignment. It creates no graphic objects. Verify, test with Quick Online View, save, then export. Locate the marker in the XML; do not assume the XML field name in advance.
In the same event-capable test context, a separate session-store probe can use the documented DL functions:
DL.AddStoreItem("DV_LOGIC_PROBE_V1", "stored by test button");
Dsp.ProbeText.Label = String(DL.GetStoreItem("DV_LOGIC_PROBE_V1"));
Verify the API in that version’s Script Assistant. Use a unique key; do not call ClearStore because it could remove other session data. Test refresh/reopen separately from restarting the Live session. Add object/array payload experiments only after the primitive probe succeeds.
For reads, use Script Assistant’s browser to insert a known read-only test parameter with correct field syntax. Preserve RtValue/status handling. Do not substitute screenshot labels for verified paths, and do not evaluate controller expressions through JavaScript eval.


Questions to answer before selecting a custom component architecture
  • Does the target Script Assistant/documentation expose a supported native element factory, child collection insertion/removal API or custom control registration mechanism? Record the exact method and reference if found; absence in these documents is not proof about all versions.
  • Can you instantiate that native object during runtime, bind a parameter with status, show it, remove it, and repeat without accumulating subscriptions? Changing a pre-existing element’s position does not pass this test.
  • Which syntax, libraries and host APIs does the installed release support? A successful TypeScript compile does not establish support for an external package’s DOM/network dependencies.
  • If using a web component, where does it run, what supported service supplies data, and how are user identity, quality, stale data and disposal handled? The iframe does not automatically share DLSYS.
  • If the structure is stable between engineering revisions, does runtime creation buy enough to justify the extra host and data integration? Pre-generated native graphics may be simpler.

06 · A maintainable Python/XML workflow
Operate on exported exchange files. “Pull a Graphics Studio file” should initially mean take a saved export from Graphics Studio. Direct database writes, editing an internal runtime cache, or automating undocumented storage are not established workflows. The supplied help documents text-editable, well-formed XML .ahc exports. [Export format]


StageWhat the tool should preserve or prove
ReaderNamespaces, identities, item types, dependency references, source metadata, scripts and unknown fields. Keep original exports immutable.
Internal modelSeparate node kind, input links, parameter paths, descriptions, quality rules and geometry. A logic parser must honor DeltaV expression semantics; a string replacement or JavaScript eval is not a parser.
TransformerMake narrow, explicit edits to observed schema fields. Preserve linked versus unlinked behavior and instance options. Regenerate IDs only by proven identity rules; never guess which IDs are references.
EmitterWrite new .ahc candidates plus a manifest: source hash/revision, generator version, target DeltaV build, changed items and required library definitions. Do not claim output is importable until it has been tested.
AcceptanceImport warnings/conflicts → Verify → inspect Studio → test operator behavior → re-export comparison. Distinguish harmless normalization from lost semantics.


Suggested experiment package — no invented .ahc schema

  00-baseline/        original saved exports
  01-title-only/      one changed property
  02-event-marker/    click and OnOpen compared separately
  03-gem-instance/    class + linked instance exports
  04-binding/        known parameter + quality behavior
  05-transform/      Python output candidates

A proposed manifest can describe the internal graph without pretending to be a native import file:
{
  "artifactKind": "proposed-logic-model-not-ahc",
  "source": "FC_20804/LOGIC$MAIN",
  "expressionVerified": false,
  "timerSemanticsVerified": false,
  "nodes": [
    {"id": "mw", "kind": "parameter", "path": "R540_TEMP/MW/ACTIVE"},
    {"id": "notMw", "kind": "not", "inputs": ["mw"]}
  ]
}
Extend that model after the first exports reveal the exact fields. A structured patcher is usually a smaller first step than a complete from-scratch XML emitter. Native import and runtime behavior remain the acceptance tests.
