    What I clarified from your sketches

    Palette ≠ library storage

    Your list of GEMs, shapes, data, batch and user-entry elements describes what the Palette exposes. Library Explorer organizes definitions; the Palette offers items for placement. The saved document contains the placed result.

    Template ≠ linked class

    A template starts a new display/contextual display/layout. A linked GEM retains a class relationship. An unlinked GEM does not. Template-based creation can still include GEMs with their own class links.

    Two different property panes

    Graphics Configuration edits the selected item. GEM Configuration Designer defines which custom options appear on instances, their types and metadata. It is not the runtime popup designer.

    Presence ≠ Visibility

    Designer Presence controls whether an option appears during configuration. Graphic Visibility controls whether content is visible. Present Online controls runtime inclusion for a group/GEM. Keep all three distinct. Designer reference · Emerson GEM guide

    Layout ≠ display set

    A layout provides screens and display frames. A display set references displays and navigation levels. A process display owns its graphic elements; a frame presents it. The same display can participate in multiple sets.

    Folders ≠ types; names ≠ behavior

    “Emerson” and other folders organize items. Color, Boolean, String and Scale are types. Label, EUVisibility, Custom Writes and SISConfirm are class-specific property names in your sketch, not universal properties on every GEM.

    Variables, timers, tabs and placeholders belong to their owner. Variables and timers attach to eligible configurations and have scope/lifetime. Tabs contain tab items within graphics. Text data placeholders belong to text/label configuration. Capture these as owned elements/properties rather than as independent top-level libraries.     Proposed design · not an implemented parser

    Preserve meaning before generating .ahc

    1. Structure

    Document identity and role; object identity/path; parent, order, geometry; source dynamo/class; assets and type information.

    2. Behavior

    Property source (literal/reference/expression); animation rules; event/handler; module context; reads/writes; navigation target; timer lifetime and shared dependencies.

    3. Evidence

    Source file and object/property/procedure location; original text; interpretation confidence; mapping rule/version; unsupported items; validation results.

    Example neutral representation — illustrative, not DeltaV XML syntax
    {
  "document": {"id": "picture:AREA_A", "kind": "operate_picture"},
  "object": {"id": "picture:AREA_A/Pump1", "kind": "placed_dynamo"},
  "property": {"name": "ModuleTag", "sourceKind": "literal", "raw": "P101"},
  "edges": [
    {"kind": "contains", "from": "picture:AREA_A", "to": "picture:AREA_A/Pump1"},
    {"kind": "opens", "from": "picture:AREA_A/Pump1", "to": "picture:PUMP_FP",
     "trigger": "click", "context": {"module": "P101"}}
  ],
  "mapping": {"targetClass": "ExampleLibrary.Pump", "status": "proposed"},
  "unresolved": ["Confirm handler and module-context extraction from source"],
  "provenance": {"sourceFile": "example-only.grf", "objectPath": "Pump1"}
}

    ModuleTag and identifiers here are proposed normalized names. A real extractor must preserve the actual source names and expressions. No vendor schema, source binary layout or target .ahc syntax is asserted by this example.

    RelationshipExampleWhy it matters
    ContainsPicture → group → shapePreserves ownership, geometry and object path.
    InstantiatesLinked GEM → GEM classPreserves reusable definition and dependency.
    ReferencesChild Fill → color standard/functionPreserves shared behavior instead of flattening a resolved color.
    CreatesTemplate → new displayCreation history is not an ongoing class link.
    Calls / opensClick → helper → popup with contextPreserves trigger, call chain and arguments.
    Reads / writesExpression or action → module parameterDistinguishes display data from a command and retains addressing semantics.

    Validate by behavior: object geometry, parameter/quality handling, displayed labels/units, click targets, context propagation, read/write semantics, repeated-open behavior, shared dependencies and linked-instance updates. XML well-formedness and import success cover only part of the result.
