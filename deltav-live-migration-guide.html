01

Scope & concepts

This guide compares the building blocks of DeltaV Operate and DeltaV Live, with particular attention to replacing VBA UserForms. Examples illustrate common requirements rather than any particular installation.

Runtime

Operator-facing customization

Buttons, animations, faceplates, dialogs, and navigation respond to operator actions or changing data. A popup containing an expandable tree is one example of a custom runtime interface.

Engineering

Configuration tools

Engineering forms can set reusable-object options, update existing graphics, or distribute outputs. Replacing these tools requires distinguishing configuration editing from runtime scripting and publication.

Separate three responsibilities.

Configuration creates or modifies the saved graphic. Runtime behavior responds to data and user actions. Deployment makes the correct version available on each workstation. One utility may perform more than one of these jobs.

.fds denotes an Operate dynamo set; .grf denotes a picture. User.fxg can hold shared VBA dependencies. Live uses GEM classes and displays, with editable .ahc XML as a configuration exchange format.

Documented means supported by the cited reference. Proposed means an implementation direction to validate. Unverified identifies a capability not established by the reviewed references.

03

What runs, and when

There is no single “scan” for all this code.

A changing pump color does not establish that a VBA or TypeScript routine runs every controller scan. An animation may simply resolve a changing parameter through its configured expression.

MechanismExecution triggerMigration question
Controller logicThe module’s configured controller execution schedule.Is the operation actually HMI behavior, or part of control logic?
Datalinks and animationsConfigured data connections and display evaluation/update behavior.Can the expression or property binding reproduce it directly?
Open / initialize handlerWhen the relevant document opens in its applicable environment.Is it preparing runtime data or changing saved configuration?
Click, keyboard, selectionThe specified user interaction.Which tag, selected item, or context is passed?
Timer / data eventThe configured timer or source-change condition.How many loaded pictures, instances, and workstations run it?
Shared helper procedureWhenever a caller invokes it.Where are all the callers and their triggers?
Dynamo Edit / configuration formThe applicable Configure-time edit or paste behavior.Which saved properties, paths or scripts does it generate?
Operate background scheduleIts configured time or data event; investigate independently of open pictures.Does the work need a persistent service or another explicit replacement?
Trace frequency, lifetime, and side effects

Record whether each trigger exists per picture, per dynamo instance, per workstation, or in a background schedule. Record writes separately from reads. A shared helper can still be called many times if every placed object owns a timer.

Confirm detailed Operate event semantics and rates against the installed-version help. The table describes trigger categories, not guaranteed execution rates.

05

The two UserForm cases

Runtime

Forms used in Operate Run

For parameter entry, status panels, selections, and normal operator actions, start with a native Live contextual display and TypeScript.

  • Replace the form’s controls with Live elements.
  • Use variables for temporary form state.
  • Map initialization and button handlers to events/actions.
  • Use documented DeltaV reads and writes.

For complex code analysis or rich trees, assess a web GUI or external desktop GUI. Those require their own data interface.

Engineering

Forms used in Operate Configure

Distinguish setting an individual graphic’s options from automating changes across existing graphics.

  • Individual options can often become GEM properties.
  • Bulk replacement and rewriting can become an external engineering utility.
  • Exported .ahc XML provides a documented file interface.
  • Import, verification, testing, and publication remain explicit stages.

A general API for an external script to manipulate the current Graphics Studio document or selection has not been established.

Start with a contextual display

Use Live controls and TypeScript actions with documented DeltaV APIs. Validate context, permissions, data quality, and open/close behavior.

What does “convert the UserForm” really involve?

Rebuild its presentation, preserve its data model and validation rules, replace platform-specific calls, then test its effects. The old VBA layout and code are evidence of requirements; they are not directly executable in Live.

Exported .frm, companion .frx assets where present, .bas/.cls code, project references, and the routines that call the form are useful assessment inputs. Keep dependent assets with the export.

References: Runtime events · GEM configuration · Exported XML · Import rules.

06

The expandable tree window

A common interface requirement is: header button → new window → expandable branches and data → useful actions or explanations. The button and popup are established capabilities. A general-purpose native TreeView has not been established in the reviewed Live documentation.

RouteWhat supports itWhat needs proving
Native Live viewerContextual displays, tables, selection, scripts, and dynamic values.Tree expansion, depth, row generation, keyboard behavior, and performance. A general-purpose TreeView was not found in the supplied reference.
Web GUILive’s embedded browser can display allowed iframe-compatible HTTP/HTTPS pages.Hosting, sandbox settings, supported browser features, data access, and actions back into Live.
External desktop GUILive can launch approved applications. Python/PySide6 provides tree widgets.Application packaging, parameter access if required, passed context, and return interactions.
Embedding is not an API bridge.

A web page shown inside Live does not automatically receive DLSYS, DL, the operator’s permissions, or access to the configuration database. A launched Python process does not inherit these objects either.

Emerson’s cited product sheet says the embedded web object dates from v14.LTS and dedicated Web Displays from v15.FP1. A Web Display can participate in display navigation. Confirm the target release before choosing the integration.

Prototype the difficult behavior first

Use a small but representative hierarchy with several depths, enough rows to require scrolling, and realistic labels. Prove expand/collapse, selected-node context, search, refresh, reopen behavior, and one representative action. Determine whether the source is exported configuration, live parameters, SQL data, or a combination before choosing the GUI technology.

References: Embedded browser constraints · Launching applications · Live table features · Web Display version information · Qt tree controls.

07

Graphics updates & distribution

Example workflow An engineering utility may update placed graphics from a revised dynamo library and distribute the results. In Live, consider linked GEM class updates first; use an external transformation tool where structural changes require it, then publish the resulting configuration.

  1. Identify the source formatOperate .grf/.fds sources need an initial conversion or deliberate rebuild. An .ahc tool operates on Live configuration exports.
  2. Export a representative Live baselineInclude the display, custom GEM class and required library dependencies. Use real exports from the target version.
  3. Transform with an engineering utilityA proposed Python GUI can select graphics, replace mapped components, preserve module references and approved local overrides, and generate a change report.
  4. Import and check the resultUse Graphics Studio. Well-formed XML is necessary but not sufficient; supported types, values and references must resolve.
  5. Test behaviorExercise the important interactions, expressions, context handling and custom scripts. Use a controlled engineering/test environment.
  6. Publish to workstationsUse Graphics Studio’s distribution mechanism for Live graphics within the same system. Handle external application files separately.

Use classes when the change is common

If displays already use linked GEM instances, a class change may cover the update. Publish all affected displays after validation. Unlinked or locally divergent components may still need transformation.

Use transformations for structural changes

Replacing object families, rewriting paths, or changing display composition can require an explicit migration rule. Preserve originals and compare meaningful properties, not just file bytes.

Publication is more than copying a file

Published configuration is retrieved by communicating workstations. Previously viewed/cached graphics can require an operator refresh; graphics not recently opened can load the newest published version when opened.

Targeted publishing is documented for displays and contextual displays. It has destination constraints designed to limit simultaneous display versions; it is not an unrestricted independent version manager for every station.

The documented workflow does not establish a public command-line/API facility for automating Graphics Studio import or publication. Keep those steps explicit until verified.

Generation is feasible, but arbitrary new XML types are not

Graphics Studio exports editable XML with an .ahc extension. The importer ignores unrecognized elements/properties and rejects invalid or out-of-range values. Adding a fabricated TreeView XML element will not create a supported native control.

Use an XML parser and representative templates. Plan for identifiers, dependencies, names, escaping, units, schema/version differences, and preserving intentional instance overrides. Repeating a migration should not duplicate objects or undo approved edits.

References: Export format · Import behavior · Linked classes · Publish lifecycle · Targeted publish.

08

Languages & extension boundaries

TechnologyUseful roleDo not assume
VBA in OperateExisting runtime forms, events, shared helpers and engineering automation.VBA procedures and UserForms will execute or automatically convert in Live.
TypeScript in LiveGraphics expressions, event/action scripts, and supported reusable logic using Live objects.Arbitrary npm packages, Node.js APIs, COM automation, or a Graphics Studio design-time API.
Python outside LiveParse/export/transform files, generate reports and configuration, or build an engineering GUI.Native execution inside a Live display or automatic access to Live’s objects and session.
JavaScript / TypeScript in a separate web GUIA rich custom tree, code viewer or application rendered by a browser.Embedding the page grants a supported bridge to DeltaV parameter or engineering APIs.
.ahc XMLExchange graphics configuration with Graphics Studio.It is a general-purpose application runtime or control-module configuration interface.

The documented Live objects are the starting point

DL handles display/session behavior such as popup opening and session storage. DLSYS handles Live-format DeltaV parameter access. DVSYS serves the documented converted-Operate addressing case. SQL queries configured data sources. ENV includes external application launching.

Library functions are defined through Graphics Studio’s supported inputs and conversion logic. They are not evidence of an unrestricted TypeScript package/module system. SQL query access is likewise not authorization or documentation for modifying the internal graphics configuration database.

Choose the runtime first, then the language.

Use native Live behavior for forms tightly coupled to operator actions and parameter access. Consider an external application for engineering automation and rich analysis, with its integration boundaries explicitly designed.

References: Emerson-provided objects · Library functions · External launching. No general package-import or engineering automation API was established in the reviewed material; that is an evidence limit, not proof that every version lacks one.

09

Trace one behavior end to end

Start with a representative custom dynamo and the updater that changes it. Expand the inventory after the first complete trace exposes the real dependencies.

.fds source → placed instance → Edit form → saved properties / pathsThen follow Run events → shared calls → faceplate/detail → parameter reads/writes → distribution and loaded versions.

Record these fields for each procedure or form

FieldWhat to capture
Location and identityProject/file, object, module, procedure, source version, local instance changes.
Trigger and lifetimeCaller, event, timer, Configure vs Run, per-instance vs per-station behavior.
Inputs and contextModule tag, selected object, parent picture, globals, files, database data.
EffectsDisplay-only changes, configuration edits, controller writes, files created/copied.
DependenciesUser.fxg, forms, class modules, OCX/DLL references, external programs, assets.
Replacement and proofNative Live, external GUI, file transformation, or unresolved; acceptance checks and results.
Acceptance checks for runtime forms
  • Correct module and context when opened from more than one graphic.
  • Validation, cancellation, access checks, and data-quality behavior.
  • Correct handling of close, reopen, minimize, and multiple instances.
  • No unexpected duplicate writes from repeated triggers or multiple workstations.
  • Tree selection, scrolling, refresh, and meaningful errors if external data is unavailable.
Acceptance checks for the graphics updater
  • Originals preserved; new outputs and a readable change report produced.
  • Module references and approved local differences survive conversion.
  • Dependencies resolve after import; no silently omitted properties.
  • Geometry, animations, actions, faceplates, and details match intended behavior.
  • A repeat run does not create duplicates or repeat unintended changes.
  • Published destination and loaded runtime version are both verified.

These checks provide a method for evaluating a migration. Documentation and file comparison alone do not establish runtime equivalence; validate representative behavior in the applicable DeltaV release.
