## New index

The new private binding-context index joins each known-role operand or captured
CPT reference leaf with a binding/identity gap to its existing source evidence.
It retains a closed category, source-use ID, optional predicate/output link,
and optional rack-candidate/address links. It does not copy raw source text,
module payloads or alias chains; the report follows those original records.

The scope includes explicit read, write and read-write slots and parsed
expression leaves. Unknown-role slots, instruction signatures, expression
containers, unparsed expressions and unparsed rungs keep their existing gap
views. A complete context index is not complete source or engineering analysis.

Existing reference operand-match records supply scope-checked rack candidates.
A unique root with a valid fully composed suffix receives a **candidate logical
address**, keyed by candidate source ID and exact suffix spelling. This namespace
is separate from confirmed relationship addresses. Each use remains distinct,
and read/write profiles come from instruction roles, not the I/O direction.
Reading an output tag remains a read. Different suffix spellings and candidates
remain separate; adapter array members are not merged with logical rack roots.

The root can match while a composed suffix is invalid: an alias ending in a
bit selector followed by another member is retained as `rack_suffix_invalid`,
with no candidate-address group. Ambiguous roots, unavailable names, scope
exclusions, absent matches, unsupported addressing, dynamic indexes, alias
cycles and invalid expanded bound identities remain distinct categories.
Expression leaves and additional access-resolver uses without an existing
reference operand match retain `rack_context_unavailable`. No new candidate is
guessed from their names in this revision.

Original reference, access, relationship and condition records remain unchanged.
Candidate context does not promote `unresolved` to `root_bound`, turn a gap
guard into a modeled guard, validate a member/bit, or establish a physical
terminal, field device, alarm consequence or runtime result.

## Basis for separating logical identity and physical backing

- The L5X format represents RackConnection and its input/output alias tags
  separately; connection data depends on the module and configuration.
  [Rockwell 1756-RM014D, September 2025, printed pp. 87–89](https://literature.rockwellautomation.com/idc/groups/literature/documents/rm/1756-rm014_-en-p.pdf)
- Rack-optimized module I/O can be referenced through its individual module
  tag or through an entry in the communication module's rack-object tag.
  Member/point structure depends on the module.
  [Rockwell 1756-RM094N, September 2025, printed p. 101](https://literature.rockwellautomation.com/idc/groups/literature/documents/rm/1756-rm094_-en-p.pdf)
- Aliases can refer to other aliases, members and bits. I/O tags are controller
  scoped. [Studio 5000: Enter Tags and Aliases](https://www.rockwellautomation.com/en-us/docs/studio-5000-logix-designer/38-01/contents-ditamap/quick-start-steps/enter-tags-and-aliases.html)
- One FLEX example maps an individual module alias into an adapter data array.
  That example is configuration-specific, not a universal slot/index formula.
  [Rockwell 1789-UM002K, January 2015, printed pp. 219–221](https://literature.rockwellautomation.com/idc/groups/literature/documents/um/1789-um002_-en-p.pdf)

The implemented candidate-only association is an inference from these documented
representations and authenticated source matches. Confirming backing memory
would require module/adapter family, revision, communication format and checked
base-tag/member mapping. Field wiring and process purpose require further
engineering evidence even after that mapping is established.
